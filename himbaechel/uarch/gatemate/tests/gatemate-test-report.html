We wrote an automated test suite for the GateMate support in nextpnr: every packed and placed design is simulated against its unpacked netlist, timing paths between all kinds of cells are checked against the vendor's timing data, and random designs exercise everything together. This page summarises what the tests found. Each bug has its own page with a reproduction, the expected and observed behaviour, when it triggers in a real design and what it does.

For a design you ship, timing is the main risk. nextpnr's timing analysis misses whole classes of paths: through 5-input LUT trees, LUTs that also feed a register, adder carry chains, comparators, FIFO flags, bidirectional pads and every output pad (bugs 31, 23, 27, 30, 5). These are in practically every design, so a design that passes timing in nextpnr can fail in the device. Until they are fixed, keep a generous margin on the reported Fmax. The bugs that produce wrong logic need netlists that a standard yosys flow rarely produces; the configuration bugs (PLL defaults, CCF pin settings) are worth checking against your designs now.

Outside nextpnr's GateMate code

O1 nextpnr common code: Fmax report crashes for related clocks without paths

Build fails

log_fmax looks up the Fmax of both clocks of a cross-clock path with at(), which throws when neither clock has register-to-register paths of its own and another clock has. With GateMate, RAMs and IO registers clocked from the fabric get their clock through a CPE of their own, which creates such related clocks. Test: GateMateTimingTest.related_clocks_without_own_paths.

common/kernel/timing_log.cc:300–304

O2 nextpnr common code: critical path report keeps the first Context

Build fails

A function-local static lambda captures the Context of the first report printed in the process; later reports from other Contexts use a deleted one. Affects programs that create several Contexts (Python scripts, test suites); the test fixture works around it.

common/kernel/timing_log.cc:43

O3 yosys cells_sim.v: CC_FIFO_40K defaults to TDP

Wrong configuration

The simulation model defaults RAM_MODE to "TDP"; the primitives library and nextpnr default to "SDP". A FIFO that leaves RAM_MODE at its default simulates as TDP and is rejected by nextpnr unless it is 80 bits wide.

techlibs/gatemate/cells_sim.v

O4 yosys cells_sim.v: FIFO words of 5 bits or more overlap in simulation

Wrong logic

The model stores FIFO word n at bit n << (15 - tp) (fifo_wraddr), which is smaller than the word width for widths of 5 bits and more, so words overlap: a written aaaaaaaaaa reads back as 55aaaaaaaa (verified with iverilog). This only affects simulation with yosys's model, but it can hide or fake FIFO bugs in a testbench.

techlibs/gatemate/cells_sim.v:1686

How the tests work

Simulation against the netlist

A three-valued cycle simulator runs the unpacked netlist with yosys's models of the CC_* primitives (cells_sim.v) and the packed and placed netlist with models of the CPE built from the Project Peppercorn schematic, and compares the outputs over random inputs. Block RAM and FIFO models follow cells_sim.v; the FIFO model was checked against iverilog over 24,000 steps. Mutation tests (swapped pins, inverted contents, wrong modes) prove that the comparison catches corrupted netlists.

Random designs

60 seeded random netlists of LUTs, multiplexers, adders, registers, IO registers, DDR, tristate and bidirectional pads and block RAMs, each simulated, checked for timing arcs and for its use of CPEs. A variant that steers around the known bugs keeps looking for new ones; the restrictions are tied to entries in known_bugs.h and go away with the bugs.

Timing

A matrix of every kind of start and end point checks that each path is analysed with the right clock edges; 48 RAM configurations check which clock each RAM pin uses; cell delays are compared with the vendor's timing database; and the simulator's cell models find every input an output depends on, each of which needs a timing arc.

Mapping quality and errors

CPE counts for adders, multiplexers and RAMs, density inside small placement regions, RAM capacity, a resource bound for every random design; and error handling for malformed constraint files, invalid parameters and unsupported configurations.

A LUT with the same signal on two inputs computes the wrong function

Wrong logicRareseen in the real flowKnownBug::LUT_SAME_INPUT

When both inputs of a LUT2 are the same net, the packer folds the function to one input and disconnects the other, but writes the folded function as a function of the input it disconnects. The output follows an unconnected input.

Expected

Observed

o follows the unconnected I1. When the LUT drives a pad directly, as in the reproduction, the packer then drops it, and the pad is left undriven.

After a DDR output with an inverter, all later outputs are inverted

Wrong logicRareseen in the real flowKnownBug::DDR_OUTPUT_INVERSION_LEAKS

is_inverted[] is declared once before the loop over all IO cells. When an output DDR register is followed by an inverter, the packer folds the inverter into the DDR inputs and sets the entries for OUT1/OUT2, and never resets them: every output packed afterwards gets its output CPE inverted.

Observed

35

An inverted clock goes through a LUT instead of the cell's clock inversion

Wastes resourcesRareseen in the real flow

A LUT inverter on a clock stays a LUT, and the registers and RAMs behind it are clocked from the fabric through it, although they can invert their clock themselves (CLK_INV, A_CLK_INV).

Expected

The global clock with the register's clock inversion.

Observed

A second global clock network, driven from the fabric through the LUT.

Reproduction

The designs below are in tests/repro/. ./run.sh 35 synthesizes them with yosys, runs nextpnr and prints the part of nextpnr's output that shows the bug.

// Bug 35: a register on the inverted global clock.
module top(input clk_in, input d, output reg q);
    wire clk, nclk;
    CC_BUFG bufg (.I(clk_in), .O(clk));
    CC_LUT1 #(.INIT(2'b01)) inv (.I0(clk), .O(nclk));
    always @(posedge nclk) q <= d;
endmodule

36

A single-bit adder that uses a mid-chain carry corrupts the carry chain

Build failsRareseen in the real flow

To find the adder that continues a chain among the users of a carry, the condition is usr.cell->type == id_CC_ADDF || usr.port == id_CI (meant: &&). If a single-bit adder uses the carry as an operand and comes first among its users, the packer gives that adder the chain's carry as its carry input and drops its own; the chain's next bit is left on CPOUT2.

Expected

a_single keeps its carry input ci2; the chain stays intact.

Observed

The netlist is corrupted; the build ends with a routing error that does not point at the cause.

Reproduction

The designs below are in tests/repro/. ./run.sh 36 synthesizes them with yosys, runs nextpnr and prints the part of nextpnr's output that shows the bug.

b36_carry_operand.v
// Bug 36: x0..x3: a 4 bit ripple-carry chain. a_single: a 1 bit adder that takes the carry
// between bits 1 and 2 of the chain (c1) as an operand, with its own carry input ci2.
module top(input [3:0] a, input [3:0] b, input b2, input ci2,
           output [3:0] s, output co, output s2, output co2);
    wire c0, c1, c2;
    CC_ADDF a_single (.A(c1), .B(b2), .CI(ci2), .S(s2), .CO(co2));
    CC_ADDF x0 (.A(a[0]), .B(b[0]), .CI(1'b0), .S(s[0]), .CO(c0));
    CC_ADDF x1 (.A(a[1]), .B(b[1]), .CI(c0), .S(s[1]), .CO(c1));
    CC_ADDF x2 (.A(a[2]), .B(b[2]), .CI(c1), .S(s[2]), .CO(c2));
    CC_ADDF x3 (.A(a[3]), .B(b[3]), .CI(c2), .S(s[3]), .CO(co));
endmodule
